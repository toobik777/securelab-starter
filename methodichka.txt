Призначення роботи
У ЛР 4 сервер уже перевіряє, чи має автентифікований користувач право на дію. Проте після 
відповіді API дані ще потрапляють у самостійне середовище виконання — браузер. Він будує 
DOM, виконує JavaScript, автоматично надсилає деякі credentials і застосовує власні мережеві 
політики. Отже, коректна серверна авторизація не робить безпечним спосіб, у який браузер 
інтерпретує текст.
Ви простежите один потік даних від поля форми або URL до DOM, безпечно відтворите 
локальний XSS-сценарій і усунете його в правильній точці — на межі інтерпретації даних 
браузером. Штатний API разом із браузерним клієнтом працює на http://localhost:5080; для 
окремого CORS-досліду ви самостійно піднімете дозволений навчальний probe на 
http://localhost:4173 і недозволений контрольний probe на http://localhost:4174. На цьому 
стенді перевірите, як actual origin впливає на доступ JavaScript до cross-origin response, 
дослідите CORS preflight і налаштуєте точний allowlist. Наприкінці, для вищих рівнів, застосуєте 
CSP та кілька browser security headers як додаткові, а не єдині захисти.
Робота виконується винятково на локальному навчальному стенді, зі штучними обліковими 
записами й даними спільного навчального набору. Заборонено перевіряти зовнішні сайти, 
надсилати дані на сторонній host, збирати cookie/token або застосовувати руйнівний payload.
Результати навчання
Після виконання роботи студент або студентка вміє:
• користуватися панелями DevTools Elements, Console, Network і Application/Storage;
• відрізняти текстові дані від HTML-коду та показати шлях source → transformations → sink;
• пояснити, чому текст, отриманий із БД або API, може залишатися недовіреним;
• відтворити контрольований stored або DOM-based XSS PoC і зафіксувати стан «до»;
• для звичайного тексту застосувати textContent, createElement та безпечні властивості

• обґрунтувати, коли продукт справді потребує sanitizer, а коли HTML взагалі не слід приймати;

Promise і await. Асинхронна функція не чекає результату, а одразу повертає Promise — об’єкт 
«результат буде пізніше» (близько до std::future). await призупиняє лише ту async-функцію, у 
якій стоїть; код, що викликав її, виконується далі. Вставте в Console (як відкрити Console і що 
робити, якщо браузер блокує вставлення, пояснено в Етапі 1, кроці 2 практичної частини); 
готовий файл — resources/copyable/example-01.js:
function later(value, ms) {
  return new Promise((resolve) => setTimeout(() => resolve(value), ms));
}
async function main() {
  console.log("1: before");
  const promise = later("done", 100);
  console.log("2:", promise instanceof Promise);
  const value = await promise;
  console.log("3:", value);
}
main();
console.log("4: main returned");

3: done

продовжилася через 100 мс, коли Promise отримав значення. Запис promise.then(f) означає

async function inspectHealth() {
    try {
        const response = await fetch("/health", { cache: "no-store" });
        const body = await response.text();
        console.log("status", response.status);
        console.log("ok", response.ok);
        console.log("body", body);
        if (!response.ok) {
            console.log("HTTP response received, but it is not successful.");
        }
    } catch (error) {
        console.log("Response unavailable; inspect Network and Console.");
    }
}

Збережіть прочитане значення у змінній і використовуйте її.
Браузер як середовище виконання
Браузерний клієнт — не лише «зображення» поверх API, а окреме середовище виконання. 
Браузер розбирає HTML, будує DOM, виконує JavaScript, обробляє події, зберігає browser 
storage, ініціює мережеві запити й застосовує власні політики безпеки. До деяких запитів він 
автоматично додає credentials, наприклад придатну для target cookie. Серверна перевірка 
доступу тому не визначає, чи безпечно клієнт вставить отримане значення в документ.
Ключовим є контекст інтерпретації. Той самий рядок браузер може сприйняти як звичайний 
текст, значення атрибута, URL, HTML-структуру або код. Якщо контрольований користувачем 
рядок потрапляє в HTML чи code context через небезпечну операцію, його символи можуть 
стати синтаксисом, а не даними.

Джерела, перетворення і DOM sinks
Джерело (source) — місце, звідки програма отримує потенційно недовірене значення. Типові 
browser sources:
• поле форми або інший user input;
• URL, зокрема query і fragment (location.hash);
• API response;
• значення з БД, яке раніше ввів користувач;
• postMessage, browser storage або third-party API.
Перетворення (transformation) — передавання, відбір, конкатенація, форматування, mapping 
чи зберігання значення між source і sink. Сам факт перетворення не є очищенням: для 
висновку треба назвати конкретну операцію та довести її властивість.
Sink — операція, у якій значення набуває певної інтерпретації. Небезпечними для недовірених 
даних можуть бути:
• innerHTML, outerHTML та insertAdjacentHTML;
• формування inline event handler або script зі string;
• eval, new Function та подібні dynamic code executors;
• запис неперевіреного URL до href чи src;
• вставлення даних в атрибут без урахування його семантики.
Натомість textContent і createTextNode створюють текстовий вузол, а createElement дає змогу 
явно побудувати структуру. Операція є безпечною не через назву сама по собі, а коли 
відповідає потрібному контексту та не переводить недовірені дані в HTML, URL або code 
context.
Карта source → transformations → sink має доводити шлях одного конкретного значення. 
Простого пошуку слова innerHTML недостатньо: потрібно встановити фактичне request field, 
response field, JavaScript transform, DOM operation і контекст інтерпретації.

досягають browser sink в інтерпретованому контексті, а браузер сприймає їх як розмітку або 
код.

Походження вебресурсу, origin і same-origin policy
Походження вебресурсу (origin) визначає комбінація scheme + host + port. Path, query і 
fragment до origin не належать. Якщо хоча б один із трьох компонентів відрізняється, origins 
різні:
• https://example.com і http://example.com — різні через scheme;
• https://example.com і https://api.example.com — різні через host;
• http://localhost:5000 і http://localhost:5173 — різні через port.
Політика однакового походження (same-origin policy, SOP) обмежує взаємодію document або 
script одного origin з resource іншого origin. Для типового fetch це насамперед означає, що 
browser code не може довільно прочитати cross-origin response. SOP не гарантує, що кожний 
cross-origin request узагалі не буде надісланий.
Origin не тотожний site. Наприклад, два порти localhost утворюють різні origins, але це саме по 
собі не доводить cross-site поведінку cookie. У цій роботі розрізнення потрібне, щоб не робити з 
CORS хибний висновок про повну модель CSRF.
CORS і передзапит preflight
Cross-Origin Resource Sharing (CORS) — механізм HTTP headers, за яким сервер оголошує, 
якому browser code з іншого origin дозволено читати response, а браузер застосовує це 
рішення. У базовому проєкті API та клієнт віддають один застосунок із http://localhost:5080, 
а Client/app.js виконує відносні запити на кшталт fetch("/api/incidents"). Якщо просто 
віддати ту саму папку Client з іншого порту, відносний fetch піде до цього статичного сервера, 
а не автоматично до API. Тому відтворюваний CORS-стенд використовує окремий probe з 
абсолютною адресою API.
Для певних cross-origin requests браузер автоматично ініціює передзапит CORS (preflight) — 
OPTIONS request до target URL перед actual request. JavaScript-код не повинен вручну підміняти 
його власним OPTIONS. Preflight містить:
• Origin — origin сторінки-ініціатора;
• Access-Control-Request-Method — method запланованого actual request;
• Access-Control-Request-Headers — перелік нестандартних request headers, якщо вони 
потрібні actual request.
Сервер відповідає CORS headers, зокрема Access-Control-Allow-Origin, а для preflight — 
потрібними Access-Control-Allow-Methods і Access-Control-Allow-Headers. Успішний preflight 
дозволяє браузеру перейти до actual request; невдала відповідь зазвичай зупиняє цей перехід. 
Натомість simple cross-origin request може дійти до API, хоча браузер не відкриє його response 
calling script.
Який запит «простий», а який потребує preflight. Простий (simple) запит — це GET, HEAD або 
POST, у якому код сторінки не додав жодного заголовка, крім кількох безпечних: Accept, Accept-
Language, Content-Language і Content-Type зі значенням text/plain, multipart/form-data або 
application/x-www-form-urlencoded. Цей перелік називають CORS-safelisted. Будь-який інший 
заголовок (наприклад, X-Lab-Cors-Probe або Content-Type: application/json) чи метод PUT, 
PATCH, DELETE робить запит «непростим»: перед ним браузер сам надсилає preflight.

fetch("http://localhost:5080/health", { headers: { "X-Lab-Cors-Probe": "stage-3" } }), 
а policy дозволяє цей origin. У Network буде два записи:
OPTIONS /health HTTP/1.1                       ← preflight, його надіслав браузер
Host: localhost:5080

• контролює доступ browser JavaScript до cross-origin response;
• не автентифікує користувача, не перевіряє ownership і не замінює authorization;
• не обмежує curl, Postman або server-to-server client, бо SOP застосовує браузер;
• не усуває XSS і не є повним CSRF-захистом;
• не гарантує, що simple state-changing request не буде надісланий.
Коли cross-origin запит має містити browser credentials, сервер указує конкретний allowed origin і 
Access-Control-Allow-Credentials: true, а client явно налаштовує credentials для fetch. 
Значення wildcard Access-Control-Allow-Origin: * несумісне з credentialed response: браузер 
не надасть такий response коду сторінки. Динамічно відбивати довільний Origin замість 
allowlist так само небезпечно.
CSP і пов’язані browser security headers
Політика безпеки вмісту (Content Security Policy, CSP) обмежує дозволені джерела ресурсів 
і деякі способи виконання коду. Директиви на кшталт script-src, style-src, connect-src та 
img-src формують allowlist для відповідних типів ресурсів. CSP може спочатку працювати 
через Content-Security-Policy-Report-Only, щоб показати violations без блокування, а після 
перевірки — через enforcement header Content-Security-Policy.
CSP є defense in depth: вона може зменшити наслідки частини ін’єкцій, але не робить 
dangerous sink безпечним. Основне виправлення XSS — не передавати недовірені дані в 
інтерпретований контекст. Невиправдані unsafe-inline або * послаблюють policy, а коректну 
policy будують за фактичними ресурсами застосунку й перевіряють на legitimate flow.
Пов’язані browser controls також мають окремі межі:
• X-Content-Type-Options: nosniff забороняє browser MIME sniffing для відповідних ресурсів, 
але не замінює правильний server Content-Type;
• Referrer-Policy керує обсягом referrer information під час переходів і requests, але не 
дозволяє безпечно зберігати secrets у URL;

Висновок про CORS робіть за браузерним спостереженням, preflight і response headers, а про 
право на ресурс — за серверними перевірками. Два localhost-порти є різними origins, але це не 
універсальний тест cross-site cookie-поведінки. MDN: Using Fetch.

macOS/Linux/Git Bash або py -3 -m http.server … у Windows: allowed probe працює на 
http://localhost:4173, disallowed probe — на http://localhost:4174, а API — на 
http://localhost:5080. Код сторінки на disallowed origin не отримує response, а Network 
містить request до абсолютної API-адреси з очікуваним Origin. Якщо такого request немає, 
це помилка топології стенда, а не доказ CORS.
2. HTTP evidence: у Development fixed state для v0.5.0 прямий HTTP client перевіряє policy 
Lab05BrowserProbe: для allowed origin Access-Control-Allow-Origin присутній і точно 
дорівнює http://localhost:4173; для disallowed origin цей header відсутній. Водночас direct 
client отримує HTTP response згідно з authentication/authorization API, що доводить: CORS не 
зупиняє сам request.
Запустіть API у Development з fixed commit, на який указуватиме v0.5.0, і виконайте:

API_URL="http://localhost:5080/health"

команду), без shell-змінних:

  -H "Origin: http://localhost:4173" "http://localhost:5080/health"

  -H "Origin: http://localhost:4174" "http://localhost:5080/health"
Очікуваний результат: обидві відповіді мають HTTP/1.1 200 OK, X-Content-Type-Options: 
nosniff і Referrer-Policy: no-referrer. Перша відповідь містить Access-Control-Allow-
Origin: http://localhost:4173; для доброго/відмінного рівня, де в policy лишився 
AllowCredentials(), також Access-Control-Allow-Credentials: true. У другій жодного Access-
Control-* немає. Тому число різних рядків залежить від вашого рівня, а не є окремим 
критерієм успіху. Статус 200 для недозволеного origin — не помилка policy: сервер запит 
виконав, а читати відповідь заборонив би браузер.
Збережіть повні response headers для обох запитів у доказах і порівняйте саме Access-
Control-Allow-Origin; не підміняйте регресію пошуком рядка WithOrigins у source code. 
Фіксований /health не потребує credentials; для інших сценаріїв використовуйте свою 
задокументовану локальну процедуру входу. Не вставляйте cookie або token до команд, shell 
history чи звіту.
